Who creates and uses each AWS role?

AWS provisioning permissions, access to Kubernetes, and permissions used by running services are separate. This step shows exactly what this configuration creates and what your team must supply.

1. Identity running Terraform

Use your existing AWS profile/SSO/CI identity, or have the Terraform AWS provider assume an existing provisioning role. The role must already exist and trust the runner. This setting creates no role, does not configure state-backend credentials, and does not change the AWS CLI or Kubernetes installer's identity.

2. Principal allowed to administer EKS

Terraform creates an EKS access entry and grants this existing role cluster-wide AmazonEKSClusterAdminPolicy access. It does not create the role or give it AWS provisioning permissions. Choose the role your installer/operators will actually assume; the cluster creator receives no automatic Kubernetes admin access.

3. Workload roles for regional storage

Create separate roles by default, or reuse roles already managed by your IAM team. Reused trust and permission policies are never modified; Terraform still creates the Pod Identity associations for this new cluster. All direct workload roles must belong to the deployment account.

The Flink bucket, role and association are provisioned as a foundation even when no Flink job is enabled. Pyroscope is provisioned only when CPU profiling is enabled in Visibility. Changing role ownership after deployment needs a reviewed Terraform state migration.

Software-only: all AWS IAM stays external.

Your new-cluster IAM choices are kept in this browser while you switch modes. This software-only request uses the role references below and excludes those new-cluster choices. Switch back to New EKS to save that separate configuration.

This path creates no IAM roles, policies, EKS access entries or Pod Identity associations. Supply the workload roles and have their owners create the exact associations below before installation. Helm service accounts and Kubernetes RBAC do not create AWS IAM roles.

Your cluster owner must also provide EKS access for the install runner, node/CNI permissions, the Pod Identity agent and EBS CSI identity. Installing the autoscaler Helm controller does not create its AWS role or association. Existing EKS with Terraform-managed regional data services is a separate CLI path described in docs/existing-clusters.md.

Role ownership and permissions

Names ending in a dash are Terraform name prefixes; Terraform generates the final suffix. Expand a role for its exact trust, permission scope and workload binding. The saved Terraform plan remains authoritative; no roles are created in this browser.

Grafana Viewer/Editor/Admin groups control the Grafana application. Kubernetes service accounts/Roles control the Kubernetes API. Neither is an AWS IAM role. IAM.md and IAM-PLAN.json are included in every download.
