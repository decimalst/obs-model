# Disposable regional acceptance lab

This separate root instantiates the unchanged regional platform module and a private SSM installation runner. It is an explicitly authorized, time-bounded live acceptance environment, not a cheaper production profile or a deployment command in the validation suite. The account ID, administrator ARN, exact reviewed AMI, expiry and generated password belong in private run inputs. No actual account or AMI is embedded in the tracked root.

The regional module starts six `m7i.xlarge` workers across three AZs and caps scaling at nine workers. The `t3.medium` runner adds two vCPUs: 26 initial and 38 maximum On-Demand Standard vCPUs before any unrelated usage in that region. Obtain the required account quota and review hourly costs before running a separately authorized plan/apply. Tags and the node cap do not enforce a dollar ceiling or automatic shutdown.

Use a dedicated encrypted regional S3 state key and lock configuration. The empty S3 backend deliberately supplies no existing production state coordinates. Retain the copied provider lock file. `terraform init -backend=false`, `terraform validate`, and `terraform test` are local syntax/mocked checks; they do not validate a deployed AWS platform. The test suite substitutes a synthetic regional module output contract for root integration checks because its discovery data sources correctly wait for the new cluster. The regional module has its own independent mock tests.

The runner has no public IP, SSH key, inbound security-group rule or AWS provisioning policy. It uses an encrypted 30-GiB root volume and IMDSv2. Its HTTPS-only outbound access reaches SSM and reviewed downloads through the lab's NAT. The only added EKS ingress is TCP 443 from this runner's security group to this lab cluster's security group. The supplied AMI must be a reviewed regional x86_64 Amazon Linux image with SSM Agent installed; user data only starts that agent. Artifact/bootstrap execution remains an explicit later SSM operation.

Runner permissions consist of `AmazonSSMManagedInstanceCore`, regional VPC discovery, exact lab cluster/association discovery, reads of the two platform Secrets, telemetry-bucket location reads and `GetObject` under this lab artifact bucket's `bundle*` keys. There is no artifact write, ECR push, IAM PassRole, IAM mutation or infrastructure provisioning permission. The role separately receives a cluster-scoped EKS Kubernetes-administrator access entry so it can install the platform; this is deliberately broad **inside this lab cluster**, including Kubernetes Secret access. Remove that runner/access entry at teardown. SSM operator authorization remains external. The standard SSM managed policy's live content is AWS-owned; it is not reduced to the custom read-only policy.

The artifact bucket is private, SSE-S3 encrypted, ACL-disabled and rejects plaintext transport. It has no automatic deletion policy and no versioning. ECR uses immutable tags, AES256 encryption and scan-on-push. Both refuse force deletion. Existing production storage deletion protection, final-snapshot behavior and telemetry versioning are unchanged. Budget/expiry review and safe cleanup remain operator procedures; `ExpiresAt` is metadata, not enforcement. Manually approved cleanup must account for retained snapshots, Secrets, buckets, images and other billable leftovers rather than declaring teardown complete when the runner disappears.

AWS references: [Pod Identity association identity](https://docs.aws.amazon.com/eks/latest/APIReference/API_PodIdentityAssociation.html) and [Systems Manager instance permissions](https://docs.aws.amazon.com/systems-manager/latest/userguide/setup-instance-permissions.html).
