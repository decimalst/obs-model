# Security setup and ownership

Security profiles configure Grafana access and produce a precise prerequisite inventory. They do **not** make the entire telemetry data plane encrypted or authenticated. The default platform namespace is a trusted administrative boundary; its tenant header and service labels are not credentials. Keep ingestion and storage private until the relevant data-plane controls below have been implemented and tested.

The profile compiler only reads local nonsecret YAML. It never contacts an identity provider, reads a Secret, creates an ingress controller, installs a mesh or changes the CNI. External policy examples remain outside the platform release. The existing networking/security owner must review and reconcile them in its own repository.

## Choose a profile

| Starting example                             | Access and authentication                                                                    | Existing resources required                                                                                       |
| -------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `examples/security-local.yaml`               | Loopback port-forward, existing local Grafana admin account                                  | Grafana admin/database/server Secrets; Kubernetes port-forward authorization                                      |
| `examples/security-oidc-ingress.yaml`        | Grafana-owned Ingress, existing TLS Secret, generic OAuth with explicit OIDC endpoints       | Existing ingress class/controller, DNS, TLS Secret, OAuth application and Secrets                                 |
| `examples/security-oidc-external-proxy.yaml` | Existing HTTPS reverse proxy owns all routing/certificates; Grafana generic OAuth            | Existing proxy namespace and route, DNS/certificates, OAuth application and Secrets                               |
| `examples/security-istio.yaml`               | Existing proxy plus existing Istio, scoped Grafana sidecar and external strict mTLS policies | Existing compatible Istio injection/CRDs, meshed proxy with exact workload identity, externally reconciled policy |
| `examples/security-linkerd.yaml`             | Existing proxy plus existing Linkerd, scoped Grafana sidecar and external identity policies  | Existing compatible Linkerd injection/CRDs, meshed proxy with exact identity, externally reconciled policy        |

HTTPS access also supports `authentication: {mode: local}` for a controlled bootstrap or recovery deployment. This uses the existing `grafana-admin` Secret and does not add SSO. OAuth requires HTTPS; loopback profiles deliberately permit HTTP only for `localhost` or `127.0.0.1` on port 3000. Services remain ClusterIP. Use `kubectl port-forward --address 127.0.0.1 -n observability service/grafana 3000:80`, never a public bind. A loopback root URL does not restrict other in-cluster callers: NetworkPolicy and Kubernetes RBAC remain necessary.

Copy an example into the private infrastructure repository, select real nonsecret endpoint/resource names and retain it with the regional deployment contract. Pass `--security-profile path/to/security.yaml` to `scripts/install.py`, `scripts/regional_values.py` or `scripts/gitops_export.py`. The installer supports `--render-only`: it emits values and prerequisites without AWS/Kubernetes calls. The validated profile is persisted in the nonsecret platform configuration so later Helm/Flux regeneration retains it. Review the full resulting diff; do not hand-edit generated Grafana values and then lose them on the next export.

To inspect a profile independently:

```sh
.venv/bin/python scripts/security_config.py examples/security-oidc-ingress.yaml \
  --output build/security-review
```

The new output directory contains `values.yaml`, `prerequisites.json` and `external-policy-examples.yaml`. The last file is an external owner's review artifact, never automatically applied by the installer. `--check-only` preflight verifies resource/key existence without deployment. Neither render nor preflight proves certificate contents, DNS, issuer trust, group claims, mesh injection or policy enforcement.

## Secrets, OAuth and TLS setup

1. Preserve the existing `grafana-admin` and `grafana-db` Secrets. Supply `serverSecretName` with a `secret-key` key shared by both Grafana replicas. Provision a high-entropy value through the organization's secret manager/External Secrets/CSI-to-Secret workflow; never put it in profile YAML or command arguments. Existing installations must retain their current Grafana encryption key during migration. Changing this key can make stored encrypted datasource credentials unreadable; use Grafana's documented encryption migration procedure and a database backup, not a blind replacement.
2. Create a confidential authorization-code client in the IdP. Register exactly the compiler's `callbackURL`, ending in `/login/generic_oauth`, and enable S256 PKCE. Require organization MFA/session rules at the IdP. Put the client ID and client secret in the existing Secret named by `authentication.secretName`, keys `client-id` and `client-secret`. Neither is embedded in generated INI; the pod resolves Secret references. This is Grafana's Generic OAuth integration against explicit endpoints, not a discovery client or issuer auto-detection mechanism.
3. Set `authURL`, `tokenURL` and `userInfoURL` to the provider's HTTPS endpoints. Keycloak-style realm paths, Okta-style authorization-server paths and Auth0-style authorize/token/userinfo paths have examples; these are templates, not verified live provider registrations. Obtain actual URLs from your provider configuration. Group claims must be an array at a simple claim path such as `groups`, `roles` or `realm_access.roles`. Configure provider mappers/custom claims when its defaults do not return groups. Provider-specific nested/URI claims that cannot meet this contract need a reviewed adapter or a future dedicated provider profile.
4. Map explicit IdP groups to `Viewer`, `Editor` or organization `Admin`. There is no default role and no Grafana server-admin mapping. Unknown/missing groups fail closed. A group may have only one configured role; a user in multiple mapped groups gets the highest mapped role. Editors/Admins can change permitted Grafana resources, so grant them narrowly. Profile scopes must include `openid`; request only the additional claims needed. Set `useRefreshToken: true` only when the provider supports it and add its required refresh scope, often `offline_access`. Group removal is not instant session revocation: profiles cap inactivity at 1 hour and absolute login life at 8 hours; revoke sessions for urgent access removal and test provider revocation behavior.
5. Publicly trusted IdPs use the container trust store. For an internal CA, set `authentication.caConfigMap` to an existing ConfigMap containing `ca.crt`; the compiler mounts that CA read-only for the OAuth TLS client. HTTPS URLs reject userinfo credentials, query strings, fragments and configuration interpolation. TLS verification cannot be disabled through the profile. Rotate CA bundles with an overlap window and a controlled Grafana restart; the mount uses `subPath`, so editing the ConfigMap alone does not refresh a running pod.
6. In ingress mode, provision an existing `kubernetes.io/tls` Secret with `tls.crt` and `tls.key` in `observability`. Match the certificate SAN to the profile hostname and configure the existing controller's HTTPS-only/HTTP-redirect policy. Merely declaring Kubernetes Ingress TLS does not guarantee its controller disables HTTP. External-proxy mode creates no Ingress; its owner must route the hostname to `grafana.observability.svc:80`, preserve the Host, overwrite untrusted forwarded headers and set `X-Forwarded-Proto: https`. Do not enable Grafana auth-proxy headers; OAuth remains the authentication boundary.
7. The generated Grafana NetworkPolicy permits the explicitly named proxy namespace on the Grafana port. It is additive to the existing regional policy, which already trusts observability/admin namespaces. It does not authenticate every pod in the proxy namespace. Use a dedicated controlled namespace and, where selected, mesh workload identity authorization. DNS, port 443 egress and IdP reachability must be available; arbitrary extra ports are deliberately rejected by these profiles.

The Ingress profile targets controllers that terminate TLS from a Kubernetes Secret and send traffic from the declared proxy namespace. AWS ALB/ACM ownership is a different path: retain the ALB/listener/certificate in its existing infrastructure repository and use `external-proxy` with an in-cluster proxy in the declared namespace. Direct ALB-to-Grafana targets need separately reviewed source-address NetworkPolicy/security-group rules and controller-specific ACM/listener configuration; declaring the ALB controller's namespace does not authorize traffic originating at the load balancer. That direct path is not a turnkey profile in this release.

The implementation is rendered against Grafana chart 10.5.15 / Grafana 12.3.1. It uses options present in that pinned version; newer documentation's ID-token validation knobs are not silently assumed to exist. Supported group mapping and PKCE behavior are documented in [Grafana Generic OAuth](https://grafana.com/docs/grafana/latest/setup-grafana/configure-access/configure-authentication/generic-oauth/) and the pinned [12.3.1 configuration](https://github.com/grafana/grafana/blob/v12.3.1/conf/defaults.ini). The IdP's authenticated token/userinfo endpoints and their CA trust are part of this boundary.

## Internal transport coverage and remaining setup

`internalTransport.mode: cluster-network` changes no data-plane TLS/authentication. `existing-mesh` currently opts **Grafana only** into sidecar injection and emits scoped inbound policy examples. No namespace-wide injection or strict policy is applied. This avoids unexpectedly breaking node-local agents, control-plane webhooks, storage quorums and existing external owners. Other mesh coverage is a separate installation-specific change, not an implicit benefit of this profile.

## Existing mesh setup and migration

The networking owner first confirms the installed mesh versions serve the generated APIs and permit Grafana sidecar injection under the cluster security policy. For Istio, review generated `security.istio.io/v1` `PeerAuthentication` with STRICT mTLS and an `AuthorizationPolicy` allowing exact service-account principals on port 3000. For Linkerd, review `Server` v1beta3 plus `MeshTLSAuthentication` and `AuthorizationPolicy` v1alpha1; confirm these versions are served by the existing CRDs. Policies select only `app.kubernetes.io/name: grafana` in `observability`. Adapt names if another Grafana instance shares that namespace, rather than broadening selectors.

Inventory all legitimate Grafana clients (proxy, monitoring, automation) and list their exact identities. The examples contain only the proxy identity. Add approved monitoring identities before enforcement; verify liveness/readiness rewriting or probe authorization. Confirm existing policies are not additive broad allows that defeat the intended restriction. The profile's NetworkPolicy may also need mesh control-plane egress in the owner's policy repository; determine the installed control-plane namespace and ports rather than opening the whole namespace/VPC. Outbound Grafana datasources remain unprotected unless both ends and their policies are separately configured.

Reconcile mesh policy through its existing owner, deploy one controlled Grafana update, then prove unauthenticated/plaintext and wrong-identity callers fail while authorized proxy, probes, OAuth and queries succeed. Check actual sidecars, certificates and authorization results. No public exposure or completion claim should depend on annotations alone. Istio's default permissive behavior and the need for strict identity authorization are explained in [Istio security](https://istio.io/latest/docs/concepts/security/); Linkerd's relevant identity resources are covered by [authorization policy](https://linkerd.io/2-edge/reference/authorization-policy/). Do not use bypass/skip-port annotations as proof of encryption.

For the rest of the pipeline, review a per-hop migration PR: certificate/identity ownership, dual-CA overlap, listener compatibility window, credential reload/restart, capacity/PDB budget, trace drains, Kafka clients/ACLs, quorum-safe storage rollouts and rollback. Remove old plaintext listeners only after all producers, consumers, maintenance jobs and support checks work through the protected path. See `docs/runbooks.md` for the stateful and trace procedures.

## Validation and recovery

`make security-test` boots pinned Grafana with chart-rendered OAuth settings, resolves synthetic Secret environment values, rejects anonymous API/local-password login and verifies the HTTPS callback/S256 challenge without following the redirect. A synthetic callback with valid saved state exercises missing-CA rejection against a loopback-only token endpoint; the same disposable instance then verifies the explicit local recovery profile. Unit tests reject credential-bearing URLs, unknown keys, injected expressions, default-role escalation, overlapping role groups and wildcard mesh identities. Helm rendering checks TLS Secret references, CA mounts, preserved DB/datasource credentials and scoped ingress admission. No real IdP or mesh is contacted.

Defer actual DNS/certificate expiry and hostname rejection, absent/wrong group rejection, Viewer/Editor/Admin permissions, refresh/revocation, missing Secret failure, private-CA rotation, mesh plain/wrong-identity rejection, network-policy enforcement and live per-hop traffic tests to the batched AWS qualification plan. Treat existence-only preflight as a prerequisite check.

Keep a reviewed local-auth recovery profile and tightly restricted Kubernetes/GitOps access. An operator may temporarily reconcile that profile and use loopback port-forward with the existing admin Secret; this is a change-controlled recovery operation, not a hidden SSO fallback. OAuth profiles disable local login and basic auth. Record access, restore the OAuth profile, revoke temporary sessions and review IdP/secret rotation. Receiver/client Secret updates supplied through environment variables need a controlled Grafana restart. Do not rotate the shared server encryption key as an ordinary OAuth client-secret rotation.
