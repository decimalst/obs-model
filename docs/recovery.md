# Recovery and upgrade preparation

The [offline qualification batch](live-qualification.md) prepares dependencies and checks the resulting evidence. Restoration, fault injection and AWS resource creation remain deferred manual operations in the account owner's chosen window. There is no automatic restore into a running database, PVC replacement, offset reset, cross-region copy or infrastructure deletion.

## Choose ownership and objectives

Use native backend mechanisms or an existing backup provider. In native mode, operations owns the version-compatible backup/export jobs, target resources and schedule; selecting `native` does not install backup jobs. In external mode, the backup owner provides the exact resource coverage, encryption/key access, consistency method, retention, restore procedure and test evidence; set `providerRef` to its reviewed runbook. An EBS snapshot without an application-consistency procedure is not sufficient evidence of a recoverable distributed database.

Set a recovery owner, RPO (maximum acceptable data loss) and RTO (time to usable intake and historical queries). The example values are null so no service promise is invented. Choose the most demanding bound that all enabled stores must meet, and attach per-store objectives/measurements to the private change record. Account for node-local Vector buffers, in-memory tail state, profile retry queues and Kafka records not yet persisted to their query store. The tool rejects a restore destination with the same account/region/cluster identity; the operator must additionally verify distinct actual endpoints, buckets/prefixes, volumes, database instances, Keeper and Kafka identities. Different context names alone are not isolation.

## Isolated restore

1. Inventory the exact pinned source revision, chart locks, image digests, CRDs, schema version, shard names/macros, topic partitions/replicas, consumer offsets, configuration and externally owned resources. Record backup IDs, completion times and a small set of synthetic known historical log IDs, metric timestamps, trace IDs and optional profile selectors. Store only nonsecret references in the qualification receipt.
2. Establish a coherent checkpoint under a reviewed write pause or the provider's tested consistency procedure. Pause KEDA during database maintenance, preserve its previous state, drain in-flight writers, and stop conflicting GitOps reconciliation at the smallest owning resource. Do not pause collectors for an unbounded interval without sizing buffers or explicitly declaring loss.
3. Create the isolated destination **later**, through a separately reviewed plan with independent state. Initially block production producers, real notification receivers and automatic reconcilers from writing to source or target. Supply restored/rotated credentials through existing Secrets and the secret manager. Give restore tools read-only access to backup sources and narrowly scoped write access to the destination.
4. Restore each enabled backend using its procedure below. Rebuild runtime configuration from the recorded Git revision; do not copy live membership identities blindly. Establish read-only queries before permitting writers or compactors. Compare known historical records and time windows, not just container startup or bucket listings.
5. Start a bounded synthetic workload in the destination. Measure missing and duplicate data, lag catch-up, quota enforcement, rule/datasource consistency and queries. Record the worst observed data gap and elapsed recovery time. Keep the source fenced until any deliberate cutover is independently approved; a successful lab restore does not authorize production failover.

### ClickHouse and Keeper

Replication protects node availability but also propagates accidental deletion. Use a qualified native `BACKUP`/`RESTORE` workflow or the existing database backup provider. Before using native backup, have the database owner configure a dedicated regional backup destination, encryption/retention and credential-free access via mounted configuration/approved identity; this chart does not currently create a ClickHouse backup role, disk or schedule. Never place S3 access keys into SQL text, query logs or receipts. Follow the pinned 25.8-compatible syntax and monitor completion IDs, rather than assuming an asynchronous request has completed. [ClickHouse backup guidance](https://clickhouse.com/docs/concepts/features/backup-restore/overview)

Cover every shard's `observability.logs_local` **and** `log_events_local`, their schema and materialized/distributed view definitions; a Distributed table is not a backup of remote shard data. Pause writers for a consistent cross-shard point. In the destination, use an independent Keeper ensemble and recorded append-only shard layout; restore the local tables without replaying materialized-view inserts into already-restored aggregates. Recreate/verify distributed views against destination hosts. Prove row/time-window checks per shard and distributed queries, then verify replication queues and quorum acknowledgements. Do not restore Keeper metadata over the live ensemble or connect new replicas to source Keeper paths. Use [the sharding migration notes](clickhouse-sharding.md) for legacy tables, TTL changes and topology expansion.

### Kafka, consumers and Mimir ingestion

Choose an application-consistent full-cluster backup supported by your provider or an explicitly engineered Kafka replication/replay design. Preserve Kafka/KRaft metadata, topic settings/partitions and consumer offsets together. Independent rolling disk snapshots of running brokers do not establish a coherent backup. Before restoring, identify the durable ClickHouse checkpoint and the available Kafka offset range; reconcile consumer resume points with it. A database snapshot plus later consumer offsets can skip lost rows; replaying earlier offsets can duplicate rows and aggregates. Record the chosen replay window and quantify duplicates. Keep the stable writer group and do not run old and restored writers against the same production topics.

Mimir 3 uses a separate ingestion topic on the regional Kafka cluster. Include its partitions, compatible ingester assignment/offset state and unflushed data in the recovery design. Restoring only old object blocks may omit recent metrics. Prove queries around the backup boundary before claiming the configured RPO. Broker additions or restored replicas do not imply partition redistribution.

### Mimir, Tempo and object storage

Create isolated destination buckets/prefixes from the reviewed backup inventory; preserve required versions and metadata and prevent target compactors from altering source storage. Restore Mimir blocks and Alertmanager state separately; provision Git-owned rules from Git rather than restoring an obsolete ruler API source. Restore Tempo object data and any compatible ingester WAL/PVC recovery path chosen for recent unflushed spans. Query both old and boundary-time samples/traces, then allow destination compaction/retention only after those checks. An object listing or versioning flag does not prove a coherent recovery point. [Mimir storage boundaries](https://grafana.com/docs/mimir/latest/configure/configure-object-storage-backend/)

Do not run current `mimirtool` mutation commands against production as a generic restore recipe. Pin a tool compatible with the deployed release and first rehearse any copy/undelete procedure on isolated buckets. The versioned-object undelete workflow requires retained noncurrent versions; record the actual recoverable interval. [Mimir block recovery tools](https://grafana.com/docs/mimir/latest/manage/tools/mimirtool/)

### Grafana PostgreSQL, Secrets and quota state

Restore PostgreSQL into a **new** RDS instance using the chosen snapshot/PITR point or the externally owned database provider. Explicitly review subnet/security/parameter groups and encryption; do not rely on restored defaults. Point only the isolated Grafana instance at it, supply matching application credentials securely and verify login, datasource access and Git dashboard provisioning. Preserve Grafana's encryption secret where required to decrypt stored database settings; rotating it without a supported migration can make saved secrets unusable. [RDS point-in-time restore](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)

Valkey admission state is a traffic-protection ledger, not exact historical billing. Choose a compatible snapshot restore or an explicitly approved fresh quota store. Snapshot age and asynchronous replication can admit an extra burst; a new store resets budgets. Keep ingestion paused/fail-closed until capacity and policy hashes are verified, then ramp a bounded test workload. Do not silently reset live keys. [ElastiCache snapshot and restore](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/backups.html)

### Optional Pyroscope and Flink

For Pyroscope v2, preserve the regional object data **and** a version-compatible metastore Raft backup/recovery procedure. The metastore indexes objects and retains durable Raft state; restoring a bucket alone is not a demonstrated profile restore. The owner must qualify the pinned release's membership/snapshot recovery into an isolated metastore, including any segment-writer buffers, and query known flamegraphs before reopening collection. If that mechanism has not been demonstrated, keep the profile recovery gate pending. [Pyroscope metastore responsibilities](https://grafana.com/docs/pyroscope/latest/reference-pyroscope-v2-architecture/components/metastore/)

For Flink, create and verify a completed savepoint using the actual application image and S3 plugin. Preserve operator UIDs, job graph/serializers, connector versions and all referenced state. Restore the job with a distinct destination and review Kafka offsets and sink idempotency before starting it; checkpointing alone does not prevent duplicate ClickHouse writes. Use the pinned job/operator lifecycle and [Flink 2.1 savepoint guidance](https://nightlies.apache.org/flink/flink-docs-release-2.1/docs/ops/state/savepoints/).

## Upgrade and roll-forward

Rehearse this exact source/target revision pair in the isolated restored environment first. Record CRD conversion/storage-version compatibility, application schema changes, Kafka metadata/storage-format compatibility, backend object-format changes and external-controller ownership. Do not infer downgrade safety from a Helm revision. Define the abort point before the first irreversible migration and a forward repair after it.

For stateless Argo workloads, reconcile a preview, run stored-signal probes through it, inspect budgets and promote one tier. Abort the preview if checks fail; preserve old pods for the routing/connection drain interval. For node agents, use bounded rolling updates and measure queue loss on node failure. Tail samplers require stable trace-ID affinity, decision-window/exporter drain, `OnDelete` and one ordinal at a time; graph pairing caches can also lose in-flight pairs. Measure these losses rather than calling the operation lossless.

For Kafka, Keeper, ClickHouse and the Pyroscope metastore, verify full health and spare capacity, replace one member at a time, wait for full replication/quorum recovery and stop on degradation. Pause KEDA around ClickHouse maintenance. Follow Mimir/Tempo pinned chart upgrade order and verify zonal membership and recent data after every stage. Never blue-green a quorum store by cloning its live identity. A ClickHouse shard/TTL migration needs explicit SQL and [migration evidence](clickhouse-sharding.md); Git rollback does not reverse data layout or retention deletion.

After an irreversible schema/storage step, use the tested forward repair image/config/migration, then repeat historical and fresh-signal queries. Resume KEDA and GitOps deliberately and verify they do not revert maintenance state unexpectedly. Preserve backups and the prior revision until the documented retention window closes. Keep failed/repeated gate receipts, including failures successfully repaired.

## Regional recovery

The default platform has independent active regions with no raw-data replication. Rehearse the surviving region's independent intake and query path, fence the failed source and document that its history is unavailable until its regional storage is recovered. Region-local recovery can qualify that limited contract; it cannot claim remote restoration of lost regional history.

For a stronger requirement, opt into `recovery.crossRegion.enabled`, a genuinely different-region destination, numeric remote RPO/RTO and a reviewed cost assessment. The setting **only records the acceptance plan**. The infrastructure owner must separately provision and price object/database/backup copies, encryption-key access, network paths and any Kafka replication. Account for steady replication bytes, request charges, duplicate storage, retrieval, restore traffic and test capacity. Measure replication lag under peak load and during source-region unavailability.

S3 replication has rules for existing objects, delete markers, versions and encryption; validate the full retained historical backup set, not only newly written objects. Kafka MirrorMaker can preserve/translate topic and group state, but topic naming, offset translation and active/passive ownership must match the writer/Mimir recovery design. Do not redirect producers or reset offsets until source fencing and replay semantics are verified. Restore the destination independently and prove historical identities plus fresh regional ingestion within the declared objectives. [S3 replication scope](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-what-is-isnot-replicated.html), [Strimzi replication architecture](https://strimzi.io/docs/operators/latest/full/overview)

After acceptance, preserve evidence and backups. Teardown requires its own reviewed data-retention and deletion plan under [the existing runbook](runbooks.md#teardown); the qualification tool never destroys resources.
